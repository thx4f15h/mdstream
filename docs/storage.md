# 存储、查询 scratch 与缓存回收测量

本实验在核心性能矩阵之外，量化语义节点、查询栈和检查点生命周期。工作负载和测量由 `tests/support/storage.rs` 共享给 `examples/storage.rs` 与 `tests/storage.rs`，无依赖和 unsafe。时间只作观测，验收基于容量、计数和独立模型。

## 复跑与原始记录

```bash
nix develop -c bash scripts/measure-storage.sh /tmp/mdtui3-storage
# 可选参数：基准字节参数、窗口查询次数、独立进程次数
nix develop -c bash scripts/measure-storage.sh /tmp/mdtui3-storage-large 16384 128 3
nix develop -c cargo run --release --example storage -- 4096 64
nix develop -c cargo nextest run --test storage
# 子索引涉及字长，另在实际 i686 二进制中验收
nix develop .#index32 -c cargo nextest run --target i686-unknown-linux-gnu --test storage
```

脚本拒绝已有目录和非法参数，保存环境、Git HEAD/脏状态、源码 SHA-256、Cargo metadata 的权威 target 目录、每轮 CSV 和日志，并逐项核对各轮非时间字段相同。每进程运行 base、4 × base、16 × base 三规模，默认 4,096 / 16,384 / 65,536；每规模 27 个阶段，共 81 个阶段、732 条指标（包括各阶段耗时）。CSV 是长表 `schema,case,scale,phase,metric,value`，schema 为 1；scale 在解析/视口场景是生成参数，在检查点场景是状态数，不等于所有场景的实际源码长度。

[原始对照 CSV](storage-baseline.csv) 保存压缩前一轮与压缩后三轮，增加 `variant,run` 两列，共 2,928 条指标。[环境记录](storage-environment.txt) 保存后三轮执行时的工具链、主机及源码摘要。环境为 ark、AMD Ryzen 7 255、Linux 6.18.54、x86_64、Rust/Cargo 1.99.1，release 默认配置；后三轮开始于 2026-10-30 15:07:18 UTC，基于 `47bc3f3a2d69f70da1750986436ce04457db9f67` 加本单元工作树。前一轮使用相同测量代码及未压缩的该提交 `src/checkpoints.rs`。前三类解析输入额外记录实际字节数及 FNV-1a 指纹。没有固定 CPU 频率、绑核或清空缓存。

## 口径与场景

- **解析**：纯文本、密集行内标记、重复引用/列表三种 ASCII 输入，4 KiB append、复用 Update，最终 finish。记录 annotation/container arena 容量、增长分配调用及解析访问数。时间不含输入生成、初始 Document 创建和结果格式化。`annotation_node_bytes` 来自当前实现初始单节点、单槽 Vec 的实际容量字节数。
- **语义查询**：在中部八个相邻起点查询 256 字节窗口，每次新建 Runs；另执行一次全篇查询，仅用于测量遍历栈峰值，不是建议的渲染策略。`Runs::scratch_stats()` 返回待处理栈帧数、实际容量字节和本迭代器累计分配/扩容调用。栈只增长，结束时容量就是该栈峰值；新迭代器重新分配。查询时间含借用片段遍历、指纹校验和 `black_box`，不等于裸索引或真实终端绘制耗时。未覆盖 DisplayCursor、搜索或其它调用链的临时分配。
- **视口输出**：固定 4 行/4 tile，预热后比较每次创建 Vec 与复用 Vec；`buffer_growth_observations` 是调用前后容量增大的次数，**不是全局 allocator 调用数**。记录实际输出容量和 tile 校验值；本场景每次最多四项，复用后容量不再增长。
- **检查点**：状态数为生成参数 / 32；相邻 tile 和间隔 97 的稀疏 tile。比较 `[u8; 256]`、`Box<[u8; 256]>`、`Vec<u8>`，顺序经历填充、clear、分帧 drain、相同位置重新填充。每状态固定 256 字节内容，Box 的已知请求字节/Vec 的实际 capacity 单独累计；两种外置 payload 各创建一次分配，内联数组没有独立分配。每阶段记录 arena、有效状态、payload、访问数与回收量。refill 时间也包含逐状态前驱查询和完整 payload 核验。

`ArenaStats::allocation_calls` 计的是受测 Vec 初次分配/容量增长请求，即使 allocator 原地扩容也记一次，不是系统调用数。`arena_capacity_bytes` 包括未用的 Vec 槽及节点内部 padding；节点内联 `Option<S>` 已含在 arena，不能再加一份内联 payload 字节。外置 payload 只加实际在用的状态，输出 Vec 的外壳容量另列。clear 不析构；drain 返回所有权后，本驱动显式 `out.clear()` 析构，计入 drain 耗时。移出而尚未丢弃的状态仍占内存，不能称为已释放。

这些是明确覆盖的容量和调用计数，**不是进程 RSS、总堆峰值或全局分配剖析**。未包含 allocator 元数据/碎片、源码和其它对象/符号 String/Vec、Update、输入构造、统计结果 Vec、栈帧及其它瞬时分配。arena 在该工作负载不缩容，所以最终容量等于自身峰值；不同生命周期的峰值不能简单相加冒充同时发生的总峰值。用户析构函数不受库的 Budget 时间保证。

## 结果与改进决策

以下解析结果选生成参数 65,536，后三轮非时间指标一致：

| 工作负载 | 实际字节 | 语义节点 | 语义 arena 字节 / 分配调用 | 容器 arena 字节 |
| --- | ---: | ---: | ---: | ---: |
| plain | 65,536 | 11 | 1,152 / 4 | 0 |
| dense | 68,067 | 110,933 | 9,437,184 / 17 | 0 |
| containers | 65,550 | 72,895 | 9,437,184 / 17 | 1,310,912 |

密集语法的主要已测容量来自语义 arena，而不是千字节级查询栈。dense/containers 都落在相同 Vec 容量台阶，不意味着活跃节点数相同。现有 72 字节语义节点仍有较大常数；进一步拆分语义/修订存储值得另做原型，但本实验没有实现拆分或测量其查找成本，不能据此声称一定节省内存或更快。相邻同类节点合并也没有覆盖已发布 ID、局部修改与增量复杂度的完整收益证明，暂不引入。

64 次窗口查询，plain 栈累计 64 次分配/扩容，dense/containers 各 192 次；单次峰值分别 288 / 1,152 / 1,152 字节。全篇查询的峰值为 1,152 / 2,304 / 2,304 字节，增长次数 3 / 4 / 4，没有按文档节点数配置 scratch。查询 scratch 复用**有明确减少重复分配的机会**，但尚无复用实现的端到端时间对照；需要设计可归还缓冲的借用 API，并测量调用链，暂不为此引入全局缓存、线程局部状态或每查询固定大数组。现有 `viewport_into` 在预热后 64 次查询容量增长为 0，新 Vec 为 64，输出校验值相同，继续使用已有复用接口即可。

**已实施的最小改进**：检查点树的两个 `Option<usize>` 子索引改为 `Option<NonZeroUsize>`（存下标 + 1，与语义树一致），读取减 1。保持 arena 顺序和树形，不进行全树压缩/重建，不改变 API、身份、版本或预算。实际节点非零大小且 Vec 分配上限小于 `isize::MAX`，因此合法节点下标 + 1 不溢出；公开 tile 上限仍由 insert 校验。

下表为 2,048 个状态，arena 包含容量余量；Box/Vec 外部 payload 各另占 524,288 字节：

| 状态/位置 | 节点数 | 节点字节，前 → 后 | arena 字节，前 → 后 | arena 降幅 |
| --- | ---: | ---: | ---: | ---: |
| 内联数组/相邻 | 4,095 | 328 → 312 | 1,343,488 → 1,277,952 | 4.9% |
| Box/相邻 | 4,095 | 72 → 56 | 294,912 → 229,376 | 22.2% |
| Vec/相邻 | 4,095 | 88 → 72 | 360,448 → 294,912 | 18.2% |
| Vec/稀疏 | 17,444 | 88 → 72 | 2,883,584 → 2,359,296 | 18.2% |

压缩前后全部非时间字段中，仅 60 个节点大小/arena 容量值变化，节点数、分配调用、写入访问、查询校验值、回收扫描量及帧数全部相同。因此保留此局部改进；不从单轮耗时声称提速。大型内联状态会被预留在每个内部节点和空槽：本例 Box 后的 arena + payload 为 753,664 字节，内联为 1,277,952 字节，但多出 2,048 次独立 payload 分配。接入方可按状态大小选择 Box，核心不强制装箱；真正的叶 payload 独立 arena/空闲表需要另测索引及回收成本。

**回收收益与边界**：2,048 状态 clear 都只有 1 次根访问，保留全部 payload；drain 后 Box/Vec 各释放 524,288 字节，而内联状态不释放独立堆容量。每帧对象/查询额度各 31，相邻树扫描 4,095 节点、133 帧，稀疏树扫描 17,444 节点、563 帧。两者均移出 2,048 个状态，失效后的逐状态 invalidate 各只访问根一次；当前有效树的移出仍可能需要 O(log T) 更新。输出 Vec 复用、每帧立即丢弃返回值；回收扫描与累计历史节点数有关，不与当前有效状态数成正比。单次预算控制的是扫描节点数，并不把用户析构或整轮扫描变成常数。

回收前后及相同位置 refill 的 arena 容量/分配调用均不变；它回收 payload，**不会归还历史树节点**。固定工作集的反复浏览适合复用现有 arena。若未来产品要求长期浏览不同位置后限制树本体，需另设计可预算的节点回收、索引重映射或重建协议；本实验未实现，也未声称 memory cap。对已释放 payload 的重复回收仍扫描历史节点，调用方应保存 cursor、按需启动新回收轮次。

## 验收边界

7 项独立测试覆盖重复非时间指标、空查询零分配、百万字窗口/全遍历 scratch 对数界、预热视口复用、独立二分区间集合的节点模型、独立插入深度/回收扫描/帧数模型、三种 payload 表示、零预算/非对称预算、部分回收与 BTreeMap 前驱模型、析构计数、旧 token 拒绝及 32 次 clear/refill 容量复用。检查点模型用 1/17/128/2,048 状态、1/97 间隔、1/31/4,096 扫描额度，不以单次机器时间定阈值。已有极值字长索引模型、随机布局和语义回归继续运行。

仅覆盖本机以及实际 i686 的功能/容量模型验证；没有总堆峰值、OOM、其它 ABI、跨机器吞吐或真实终端布局结论。查询 scratch 复用、语义/修订拆分、节点本体回收与完整内存剖析仍是后续工作。
